## 📌 DB 인덱스란

---

데이터베이스 테이블에서 **검색 성능을 향상**시키기 위해 사용하는 자료 구조로, 주로 **WHERE 절, JOIN, ORDER BY** 등에 활용된다.

- 인덱스는 항상 최신의 정렬 상태 유지
- 인덱스도 하나의 데이터베이스 객체
- 데이터베이스 크기의 약 10% 정도의 저장공간이 필요

## 📌 인덱스 알고리즘

---

### 1️⃣ Full Table Scan

<img src="/assets/img/cs/02/cs02_1.png" alt="velog 404" style="max-width: 600px; max-height: 400px;">

> **❓ 페이지(Page)**  
> DB에서 데이터를 저장하고 관리하는 최소 단위 (InnoDB 기준 16KB)

- 순차 I/O 방식으로 액세스하기 때문에, 인덱스 사용 시 발생하는 랜덤 I/O보다 디스크 액세스 비용이 낮을 수 있음
- 적용 가능한 **인덱스가 없는** 경우 사용
- (인덱스가 있더라도) 인덱스로 필터링되는 **데이터 범위가 넓은 경우** 사용
  > ❗ MySQL 옵티마이저는 InnoDB 테이블에 대해, 조회 대상이 **전체 행의 약 20~30% 이상**일 경우 비용 기반 판단에 따라 인덱스 대신 Full Table Scan을 선택하는 경향이 있음
- (인덱스가 있더라도) 크기가 **작은 테이블**에 **액세스**하는 경우 사용

### 2️⃣ B+Tree

<img src="/assets/img/cs/02/cs02_2.png" alt="velog 404" style="max-width: 600px; max-height: 400px;">

> **❓ B+Tree**  
> 데이터베이스와 파일 시스템에서 디스크 I/O를 최소화하기 위해 설계된 균형 트리 기반 인덱스 자료 구조
> 특징: 모든 리프 노드의 깊이가 동일, 하나의 노드가 여러 개의 자식 노드를 가질 수 있음

- 동일한 조건에서 Full Table Scan 대비 **탐색 횟수가 크게 감소**하여 `SELECT` 성능이 향상됨
- 그러나, `INSERT` 시에는 페이지 분할로 인한 DB 성능 저하 가능
- `UPDATE`, `DELETE`는 WHERE 절로 처리 대상을 찾기 위한 **조회 성능은 향상**되지만, 사용되지 않는 인덱스가 많을 경우 불필요한 **처리량 증가**, **페이지 낭비**, **인덱스 조각화**가 발생할 수 있음
  > ❗ **InnoDB 기준**
  >
  > - **DELETE**는 실제 데이터를 즉시 제거하지 않고 delete-mark 처리
  > - **UPDATE**는 인덱스의 기존 레코드에 delete-mark 처리 후, 새 레코드를 삽입

## 📌 인덱스 종류

---

<img src="/assets/img/cs/02/cs02_5.png" alt="velog 404" style="max-width: 600px; max-height: 400px;">

### 1️⃣ 클러스터링 인덱스

**id** 컬럼에 클러스터링 인덱스를 적용해보자.

```sql
// 생성 방법 1. PRIMARY KEY 제약조건
ALTER TABLE member
ADD CONSTRAINT pk_id PRIMARY KEY (id);

// 생성 방법 2. 한 컬럼에 NOT NULL, UNIQUE 제약조건 동시에
ALTER TABLE member MODIFY COLUMN id int NOT NULL;
ALTER TABLE member ADD CONSTRAINT nuq_id UNIQUE (id);
```

<img src="/assets/img/cs/02/cs02_3.png" alt="velog 404" style="max-width: 600px; max-height: 400px;">

- 클러스터링 인덱스를 적용한 컬럼을 기준으로 **실제 데이터**가 **정렬**
- 테이블 당 **1개**만 존재 가능
- **리프 페이지**가 **실제 데이터**를 담고 있음

### 2️⃣ 논-클러스터링 인덱스

**name** 컬럼에 논-클러스터링 인덱스를 적용해보자.

```sql
// 생성 방법1. 한 컬럼에 UNIQUE 제약조건
ALTER TABLE member
ADD CONSTRAINT unq_name UNIQUE (name);

// 생성 방법2. UNIQUE 인덱스 생성
CREATE UNIQUE INDEX unq_idx_name
ON member (name);

// 생성 방법3. 인덱스 생성
CREATE INDEX idx_name
ON member (name);
```

<img src="/assets/img/cs/02/cs02_4.png" alt="velog 404" style="max-width: 600px; max-height: 400px;">

- 실제 데이터 페이지는 그대로
- 별도의 인덱스 페이지 생성 -> **추가 공간** 필요
- 테이블당 여러 개 존재 가능
- **리프 페이지**가 실제 데이터 페이지의 **주소**를 담고 있음

### 3️⃣ 클러스터링 인덱스, 논-클러스터링 인덱스 함께 적용

**id** 컬럼에 클러스터링 인덱스, **name** 컬럼에 논-클러스터링 인덱스를 적용해보자.

<img src="/assets/img/cs/02/cs02_6.png" alt="velog 404" style="max-width: 600px; max-height: 400px;">

- 논-클러스터링 인덱스 리프 페이지에 **실제 데이터 페이지 주소**가 아닌 **클러스터링 인덱스**가 적용된 칼럼의 **PK 값**이 저장됨
- 이는 클러스터링 인덱스에서 **페이지 분할**이 발생할 때, 논-클러스터링 인덱스의 리프 페이지의 값을 계속 변경하지 않기 위함

## 📌 인덱스 적용 기준

---

### 1️⃣ 카디널리티 (그룹 내 요소의 개수)가 높은 것 = 중복 수치가 낮은 컬럼

<img src="/assets/img/cs/02/cs02_7.png" alt="velog 404" style="max-width: 400px; max-height: 400px;">

→ id, 이메일, 주민번호

### 2️⃣ WHERE, JOIN, ORDER BY 절에 자주 사용되는 컬럼

- 인덱스는 추가 공간이 필요하고 조건 절이 없다면 인덱스가 사용되지 않기 때문

### 3️⃣ INSERT / UPDATE / DELETE가 빈번하지 않은 컬럼

### 4️⃣ 규모가 작지 않은 테이블

## 📌 인덱스 사용시 주의사항

---

### 1️⃣ 잘 활용되지 않는 인덱스는 과감히 제거하자

- WHERE 절에 사용되더라도 자주 사용해야 가치가 있다
- 불필요한 인덱스로 성능저하가 발생할 수 있다

### 2️⃣ 데이터 중복도가 높은 컬럼은 인덱스 효과가 적다

### 3️⃣ 자주 사용되더라도 INSERT / UPDATE / DELETE가 자주 일어나는지 고려해야 한다

- 일반적인 웹 서비스와 같은 온라인 트랜잭션 환경에서 쓰기와 읽기 비율은 2:8 또는 1:9이다
- 조금 느린 쓰기를 감수하고 빠른 읽기를 선택하는 것도 하나의 방법이다

인덱스는 만능 해결책이 아니라, **조회 패턴과 데이터 특성**에 맞게 설계해야 하는 성능 최적화 도구입니다.
