①② 사용자가 웹 브라우저를 통해 찾고 싶은 **웹 페이지의 URL 주소**를 입력
③ 사용자가 입력한 URL 주소 중에서 `Domain name` 부분을 `DNS 서버`에서 검색
④ `DNS 서버`에서 해당 `Domain name`에 해당하는 `IP 주소`를 찾아 **사용자가 입력한 URL 정보**와 함께 전달
⑤⑥ **웹 페이지 URL 정보와 전달받은 IP 주소**는` HTTP 프로토콜`을 사용하여 `HTTP 요청 메시지` 생성, 이렇게 생성된 `HTTP 요청 메시지`는 `TCP 프로토콜`을 사용하여 인터넷을 거쳐 해당 `IP 주소`의 컴퓨터로 전송됨.
⑦ 이렇게 도착한 **HTTP 요청 메시지**는 `HTTP 프로토콜`을 사용하여 **웹 페이지 URL 정보로 변환**
⑧ `웹 서버`는 도착한 웹 페이지 URL 정보에 해당하는 **데이터를 검색**
⑨⑩ 검색된 웹 페이지 **데이터**는 또 다시 `HTTP 프로토콜`을 사용하여 `HTTP 응답 메시지` 생성, 이렇게 생성된 `HTTP 응답 메시지`는 **TCP 프로토콜**을 사용하여 인터넷을 거쳐 원래 컴퓨터로 전송
⑪ 도착한 `HTTP 응답 메시지`는 `HTTP 프로토콜`을 사용하여 웹 페이지 데이터로 변환
⑫ **변환된 웹 페이지 데이터**는 **웹 브라우저에 의해 출력**되어 사용자가 볼 수 있게 됨

### 📌 DNS 서버 요청

---

사용자가 `naver.com` URL을 입력하면  
👉 **가장 먼저 브라우저 내부의 DNS 캐시** 확인
👉 브라우저에 없으면, **운영체제 수준에서도 DNS 캐시** 확인

> **DNS 캐시란**
>
> - 최근에 요청한 도메인에 대한 **IP를 기억**하고 있는 **로컬 메모리 캐시**
> - 같은 요청이 들어오면 DNS 서버까지 가지 않고 **바로 응답**할 수 있음

👉 캐시에 없으면, **설정된 DNS 서버에 질의**

<img src="/assets/img/cs01_2.png" alt="velog 404" style="max-width: 600px; max-height: 400px;">

`서버`: 내가 DNS 질의를 보낸 서버 이름 (KT DNS 서버)
`Address`: 해당 DNS 서버의 IP 주소
`Addresses`: 로드 밸런싱 or 이중화를 위한 여러 IP, 사용자의 위치나 서버 부하 상태에 따라 하나의 IP로 연결

> **참고: DNS 서버는 어디에 있을까?**
>
> - 통신사(ISP)에서 제공하는 DNS 서버
>   → 예: KT 사용자라면 `168.126.63.1`, `168.126.63.2`
> - 공용 DNS 서버 (누구나 사용 가능)
>   → 예: 구글 DNS: `8.8.8.8, 8.8.4.4`, Cloudflare DNS: `1.1.1.1, 1.0.0.1`, 네이버 DNS: `223.130.195.95`, `223.130.200.104`

### 📌 HTTP 요청 메시지 생성

---

👉 `naver.com` URL에 대한 IP 주소를 확보한 후,
브라우저는 URL `https://naver.com/index.html`를 분석

| 구성 요소     | 설명                                 |
| ------------- | ------------------------------------ |
| `https://`    | HTTPS 프로토콜                       |
| `naver.com`   | 도메인 이름 (DNS를 통해 IP로 변환됨) |
| `/index.html` | 요청 경로                            |

👉 브라우저는 위 정보를 바탕으로 아래와 같은 **HTTP 요청 메시지** 생성

```text
GET /index.html HTTP/1.1
Host: naver.com
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) ...
Accept: text/html
Connection: keep-alive
```

`GET`: 요청 방식 (GET/POST 등)
`/index.html`: 요청 경로
`Host`: 어떤 도메인을 요청하는지 (가상호스팅 시 중요)
`User-Agent`: 사용자의 브라우저 정보

### 📌 HTTP 메시지의 캡슐화와 TCP 3-way 핸드셰이크

---

👉 브라우저가 만든 **HTTP 메시지**는 전송을 위해 TCP 헤더가 추가

> 이때, **TCP 헤더**의 `flags`라는 필드에 `SYN`, `ACK`, `FIN`등의 제어 비트가 설정되고, 이후 1계층까지 도달하여 전기/무선 신호로 바뀌는 순간, **3-way handshake**의 첫 번째 `SYN 패킷`이 실제 전송

👉 생성된 `TCP 세그먼트`는 아래 계층으로 내려가며 **IP 헤더**, **MAC 헤더** 등 각 계층의 정보가 추가되며 **캡슐화**

<img src="/assets/img/cs01_3.png" alt="velog 404" style="max-width: 600px; max-height: 400px;">

👉 **1계층**까지 도달하면, 데이터는 전기/무선 신호로 변환되어 네트워크를 통해 전송

> `SYN` : TCP 연결을 맺기 위해 처음 보내는 요청 신호
> `ACK` : 상대방의 SYN(또는 데이터)을 잘 받았다는 응답 신호

### 📌 웹서버

---

👉 웹 서버는 `TCP 연결`을 통해 전달받은 **HTTP 요청 메시지**를 해석
👉 웹 서버는 요청에 맞는 웹 페이지 데이터 검색

- `GET /` 요청이면, 메인 페이지에 해당하는 HTML 파일을 찾음
- **동적 페이지**일 경우 백엔드 서버가 로직을 실행해서 HTML 생성, **정적 페이지**일 경우 HTML, CSS, JS 파일을 바로 가져옴
  👉 웹 서버는 `HTTP 프로토콜`로 **응답 메시지**(상태 코드, 응답헤더 포함) 생성

```text
HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Content-Length: 8253

<html>...</html>
```

### 📌 이후 과정

---

👉 **HTTP 응답 메시지**는 `TCP 프로토콜`을 이용해 인터넷을 통해 클라이언트로 전송
👉 브라우저는 **HTTP 응답 메시지**를 해석하여 **웹 페이지 데이터**로 변환

- HTML 파싱 → DOM 생성
- CSS 파싱 → CSSOM 생성
- JS 실행, 이미지 등 추가 자원 요청
- DOM + CSSOM → 렌더 트리 생성
- 레이아웃 계산 → 화면에 그리기(Painting)
